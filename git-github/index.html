Git & GitHub Workflow

Every week becomes a traceable checkpoint

Use Git history as development evidence. Commit meaningful, tested increments instead of one large final upload.

Core workflow

Terminal · bash
git status
git add .
git commit -m "Complete Week 04 Flexbox and Grid layouts"
git push
  1. status: inspect what changed.
  2. add: stage intended files.
  3. commit: create a named checkpoint.
  4. push: send it to GitHub.

Repository setup

First time · bash
git clone YOUR_REPOSITORY_URL
cd YOUR_REPOSITORY
git status

Keep the root README clear, use predictable folders, and do not commit private keys, passwords or unrelated files.

GitHub Pages deployment

1. Push a working site

Make sure index.html and relative asset paths work in the repository.

2. Open Repository Settings → Pages

Choose deployment from a branch when using a simple static site.

3. Choose the branch/folder

For this course repository, publishing from the main branch root is the simplest option.

4. Open the public URL

Test navigation, CSS, JavaScript, images and Fetch paths at the live URL.

Common Git problems

Push rejected?
Read the Git message. You may need to pull remote changes, resolve conflicts, test, commit the resolution, then push again.
Wrong files committed?
Do not delete history blindly. Identify the unwanted files, update .gitignore where appropriate, remove them in a new commit, and push the correction.
Pages shows 404?
Check the configured branch/folder, confirm index.html exists there, and inspect links/asset paths for project-site relative-path issues.
